## 一、定位变化

| 维度 | 现状（for PM） | 目标（for CE 部门） |
|---|---|---|
| 服务对象 | 单一 PM（IC、执行导向） | **三类人群**：中央市场 PM / 区域市场（PST）/ 销售管理层（圈长 LEL 及以上） |
| 核心动作 | 个人执行 | 个人执行 **+ 团队管理 + 跨层级对齐 + 数据决策 + 全渠道客户互动** |
| 新增职能属性 | — | People management（教练/绩效/1:1）、辖区运营、区域落地、客户分层与覆盖 |
| 疾病领域 | Hematology | 不变 |
| 三角色 | 助理+参谋+赋能 | 不变（但每角色需覆盖三类人群场景） |

**根本影响**：从"单人格"变为"**多人格**"。会话启动时智能体须先识别用户属于哪类人群，再匹配场景。这是所有技能改动的前提。

**人格识别方式（已定 = 选项 A + 持久化记忆）**：

- **首次环境创建时**：会话开头主动问一组开场问题（一次问全，避免多轮打断）：
  1. **你是哪类角色？** 中央市场 / 区域市场（PST）/ 销售管理（圈长及以上）
  2. **负责哪些区域 / 项目？** 如销售大区（东/南/西/北/中）、省份、负责的产品或项目
  3. **向谁汇报？** 直接上级角色（如 PM→MM、PSM→PSL、LEL→REL 或 RCL）
- **答完即写入 profile，之后不再重复问**（借鉴 workspace 的 profile 机制，已实证可用）：
  - `.claude/skills/profile.yaml`（**进 git**）：存**角色信息**——`role`（central-marketing / pst / sales-mgmt）、`ta`（Hematology）。fork 后可直接改。
  - `.claude/skills/profile.local.yaml`（**不进 git，.gitignore 排除，但留在环境磁盘每次启动稳定可读**）：存**个人身份信息 PII 与工作上下文**——`name` / `email` / 具体职级（如 PSM/PSL/LEL）/ **负责区域**（东/南/西/北/中或具体省份）/ **负责产品或项目** / **汇报对象**（上级角色与姓名）。首次由 `profile.local.example.yaml` 复制改名，或由智能体按开场问答自动填入。
  - **AGENTS.md 第 2 节会话启动流程**新增一步：**先读 `profile.yaml` 的 `role`**——已配置则直接按该角色进入，跳过询问；未配置（值为空）才问，问完写回文件。
- **为什么放 `.claude/skills/`**：Ona 环境扫两个目录，但本地 Claude Code（VS Code）只读 `.claude/`；`.claude/skills/` 是两端交集，profile 放这里两个 runtime 都能读到。（workspace 已验证）

> ⚠️ PII 合规：他人姓名/手机/邮箱/KOL 行程等敏感信息**禁止**写进任何进 git 的文件。`profile.local.yaml` 只放用户本人信息。

## 二、罗氏 CE 部门组织结构（已知部分，其余待补充）

> 本节内容用于知识包 `org/department.md`。**部门完整架构设为后续待补充**，以下为当前已确认信息。

### 已确认的汇报线

**中央市场线（Central Marketing）**
```
PM（IC，中央市场产品经理）
  └→ MM（Market Manager）
       └→ Franchise Head（FH）
```

**区域市场线（PST = Patient Solution Team，罗氏特色）**
```
PSM（Patient Solution Manager，一线区域市场经理）
  └→ PSL（Patient Solution Lead，PST 长官）
       └→ RCL（生态群长官）
```

**销售管理线**（LEL → RCL 有两条路径，视区域是否设 REL）
```
圈长 LEL（Local Ecosystem Lead，地区经理）
  ├→【有 REL 的区域】→ REL（Regional Ecosystem Lead）→ RCL
  └→【无 REL 的区域】→ 直接向 RCL 汇报
```

**关键：RCL 与 MM 平级，均向 FH 汇报**
```
                    Franchise Head（FH）
                   /                    \
          MM（中央市场）            RCL（生态群长官）
              |                    /        |
           PM（IC）            PSL        REL（部分区域）
                                |          |
                              PSM         LEL（圈长）
                                          （无REL区域LEL直接→RCL）
```
> RCL 同时是**区域市场线（PSL）**与**销售管理线（REL/LEL）**的汇聚点，向 FH 汇报，与中央市场的 MM 平级。

### 罗氏特色术语表（供智能体理解用户身份）

| 缩写 | 全称 | 中文 | 层级 |
|---|---|---|---|
| PM | Product Manager | 中央市场产品经理 | 中央市场，IC |
| MM | Market Manager | 市场经理 | 中央市场，PM 的上级 |
| PST | Patient Solution Team | 患者解决方案团队 | 区域市场团队 |
| PSM | Patient Solution Manager | 一线区域市场经理 | 区域市场，IC/一线 |
| PSL | Patient Solution Lead | PST 长官 | 区域市场，PSM 上级 |
| LEL | Local Ecosystem Lead | 圈长（地区经理） | 销售管理，一线管理层 |
| REL | Regional Ecosystem Lead | 区域生态群长官 | 销售管理（**仅部分区域设置**） |
| RCL | Regional Cluster Lead | 生态群长官 | PSL / REL / LEL 的汇聚上级，**与 MM 平级，向 FH 汇报** |
| FH | Franchise Head | 事业部负责人 | MM 与 RCL 共同的上级 |

**汇报路径要点：**
- RCL 与 MM **平级**，同向 FH 汇报。
- LEL → RCL 有**两条路径**：设 REL 的区域走 LEL → REL → RCL；未设 REL 的区域 LEL 直接 → RCL。
- REL **仅部分区域存在**，智能体识别销售管理线用户时需先确认其区域是否设 REL。

## 四、业务技能（`skills/`）需要增加的方向

### 4.0 技能形式规范（渐进式披露，借鉴 workspace，已定）

**新技能全部采用 workspace 验证过的渐进式披露结构**，避免单文件过长、每次全量加载：

```
skills/<skill-name>/          # 从单文件 <skill>.md 升级为目录
├── SKILL.md                  # 主文件，控制在 ~60-80 行：
│                             #   - YAML frontmatter：name / description（含触发词）/ tier / uses / freq
│                             #   - 何时用 + 角色分流表（中央/区域/销售）+ 工作流骨架（场景→触发说法→一句话）
│                             #   - 合规注意 + 「参考文件」索引表（需要什么 → 读哪个 reference）
├── references/               # 详细内容，按需读
│   ├── workflows.md          #   各场景的逐步流程 / 代码 / 表格
│   └── <topic>.md            #   分层定义、策略矩阵、计算方法等
└── templates/                # 可复用产出模板（可选）
```

**要点（对标 workspace 实测范本 `kol-engagement`，SKILL.md 仅 75 行 + 4 个 references）：**
- **description 短而含触发词**：一句话定位 + `Triggers on "..."` 中英触发语列表，供智能体匹配。
- **角色分流放 SKILL.md 主表**：用一张表区分中央/区域/销售三类人群的覆盖范围与重点（对应 workspace 的「CMM vs MSM」分流表）。这是多人格的落地方式——技能通用，内部按角色分岔，不为每类人群建三套。
- **重内容下沉 references**：SKILL.md 只放骨架与索引，逐步流程/数据表/模板放 `references/`、`templates/`，用「需要什么→读哪个」索引表指向。
- **现成可复用**：workspace `kol-engagement/references/hospital-tiering.md` 已是 C30/T70/T300 医院分层的完整范本，本仓 `customer-segmentation` 可直接对标其结构。

## 八、客户/医院分级体系（已从 Drive 读取，✅ 已解锁）

> 来源：`2025年T300医院list.xlsx`（Drive id `17drlxZ92xNITE1hjwcePI50RiHFohntN`，修改于 2026-06-28），
> 经 Google Workspace OAuth 授权后用 `google-workspace` 技能读取解析。**这是 `customers/segmentation.md` 的核心数据。**

### 医院三级金字塔分层

血液领域目标医院按**销售/覆盖价值**分为嵌套的三级（下级包含上级）：

```
        C30   ── 30 家 ── 核心医院（最高优先级）
         │
        T70   ── 70 家 ── 第二级
         │      （C30 + T70 = T100，顶级 100 家，xlsx Level 列已证实）
         │
        T300  ── 全部 300 家目标医院（T100 + 额外 200 家）
```

| 层级 | 医院数 | 定位 | 备注 |
|---|---|---|---|
| **C30** | 30 | 核心医院，最高覆盖优先级 | 5 大区分布：北 11 / 东 7 / 中 7 / 南 4 / 西 1 |
| **T70** | 70 | 第二级重点医院 | 5 大区分布：北 19 / 中 15 / 东 14 / 南 13 / 西 9 |
| **T100** | 100 | = C30 + T70，顶级医院 | xlsx `T100` 表用 Level 列标注每家属 C30 还是 T70 |
| **T300** | 300 | = T100 + 额外 200，全部目标医院 | 覆盖 29 省 |

### 数据字段（分级表 schema）

`Level（C30/T70）| 序号 | 医院编码 | 医院名称 | 销售大区 | 省份 | 城市`

- **销售大区**：全国分 **5 大区** —— 东区 / 南区 / 西区 / 北区 / 中区（对应销售管理线的辖区维度）
- **医院编码**：如 `SH012`（上海）、`BJ089`（北京）、`TJ047`（天津），省份缩写 + 序号
- xlsx 还含 `Pivot Table 1`（列头 Medical/Rui/Lei/Ting = **医学事务部区域医学经理的负责分工**，与 CE 部门无关，本项目忽略）
