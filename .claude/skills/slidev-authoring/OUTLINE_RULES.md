# Outline Writing Rules

提纲是 slides 的唯一内容来源（SSOT）。提纲的写法直接决定 slides 能否无损迁移。提纲不是"写文章"，而是"为视觉化准备结构化素材"。

---

## Rule 1: 每页结构 — 标题 + 语义块 + speaker notes

```markdown
## Slide N: 标题

引导句（1-2 句，告诉观众这页看什么、为什么看）

**语义块标题**（不带冒号）

内容（表格/分段/代码块）

> Speaker notes：演讲时的口头补充，不上 slide。
```

- `## Slide N: 标题` — 每页一个二级标题
- 引导句紧跟标题，不加粗，不用 `>` 标记
- 语义块用加粗标题分隔
- Speaker notes 用 `>` 标记，与正文明确分离

## Rule 2: 加粗标题不带冒号

```markdown
<!-- ❌ -->
**四个驱动力（每项附具体数据点）：**

<!-- ✅ -->
**四个驱动力**
```

冒号在视觉控件中没有意义，且会导致验证脚本匹配失败。需要补充说明时写成独立引导句：

```markdown
**四个驱动力**

每项附具体数据点，展示多个因素同时成熟：
```

## Rule 3: 表格只用于多维对比

**用表格**（读者需要横向扫描同一行）：
- 逐维度对比：CC vs ONA（维度 × 方案）
- 特性矩阵：功能 × 支持情况
- 规格列表：参数 + 值 + 说明

**不用表格**（每个条目独立阅读）：
- N 个并列概念 → 分段（每段有标题+描述）
- 步骤流程 → 编号列表
- Do/Don't 对照 → 分段或列表

判断标准：把表格每行拆成独立段落，信息是否完整且不依赖其他行？是 → 不该用表格。

```markdown
<!-- ❌ 并列概念用表格 — slides 会转卡片，必然改写 -->
| 驱动力 | 变化 | 数据点 |
|--------|------|--------|
| 模型能力提升 | 从聊天到推理... | SWE-bench: 1.7%→72.7% |

<!-- ✅ 并列概念用分段 — slides 直接映射为卡片 -->
**● 模型能力提升** — 从"能聊天"到"能干活"。推理、规划、执行能力指数级增长。
数据点：SWE-bench: 1.7% → 72.7%（18 个月，40 倍）
```

## Rule 4: 表格单元格 ≤ 40 字

超过 40 字的单元格在 slides 中会溢出或被迫换行。

处理方式：
- 拆分为主句（放单元格）+ 补充（放 speaker notes）
- 或改用分段格式（Rule 3）

```markdown
<!-- ❌ -->
| 模型能力 | SWE-bench：GPT-4 (2024.1) 1.7% → Claude Sonnet 4 (2025.6) 72.7%，18 个月提升 40 倍 |

<!-- ✅ -->
| 模型能力 | SWE-bench: 1.7% → 72.7%（18 个月，40 倍） |
```

## Rule 5: 数据点独立成行

数据点不要嵌在描述句中间。Slides 中数据点通常用不同颜色/字号单独展示。

```markdown
<!-- ❌ -->
AI 从实验室走向每个开发者，GPT-4 发布时 $30/M tokens，现在等效能力 $3/M。

<!-- ✅ -->
AI 从实验室走向每个开发者。ONA 直接免费提供 Claude Opus。
数据点：API 价格 18 个月降 10 倍（$30 → $3/M tokens）
```

## Rule 6: Speaker notes 与正文边界清晰

Speaker notes（`>` 标记）是演讲时的口头补充，不上 slide。

判断标准：
- 脱离演讲语境后仍有信息价值 → 放正文
- 只在演讲时有意义（"后面我们会看到..."、"回顾 Slide 4"） → 放 notes
- 引导句、过渡句、类比 → 放正文
- 详细数据的完整版本 → 放 notes（正文放精简版）

```markdown
<!-- 正文 -->
和人类记忆很像——常用的记得住，用过就忘的自然淡化。

<!-- Speaker notes -->
> 这是 Context Engineering 最核心的一条。实际案例：本次演讲提纲经历了 10+ 轮讨论...
```

## Rule 7: 每页内容量预估

写提纲时预估 slides 的纵向空间占用，避免生成时才发现溢出。

| 内容类型 | 高度预算 |
|---------|---------|
| 页面标题 | ~8% |
| 引导句（1-2 行） | ~5% |
| 表格（含表头，N 行） | ~(5+N×4)% |
| 分段卡片（N 个） | ~(N×12)% |
| 终端窗口（N 行） | ~(8+N×4)% |
| 底部锚点 | ~8% |

总和超过 85% 就有溢出风险。超过时：
1. 优先拆分 speaker notes 中的内容
2. 其次考虑拆页（两页标题体现从属关系）
3. 不要压缩正文措辞来省空间

## Rule 8: 交叉引用不写进正文

"回顾 Slide 4"、"详见 Slide 21" 放 speaker notes，不放正文。

## Rule 9: 语义块标注信息类型

加粗标题暗示信息类型，帮助 slides 生成时选择控件。

| 信息类型 | 提纲写法 | Slides 控件 |
|---------|---------|------------|
| 并列概念 | 分段（每段有标题+描述） | 卡片网格 |
| 多维对比 | 表格（3+ 列） | Markdown 表格 |
| 流程/演化 | 编号列表或代码块 | 终端窗口/时间线 |
| 核心结论 | 独立段落，加粗 | 高亮条带 |
| 引用/心法 | blockquote（标注为正文级） | border-left 引用块 |
| Do/Don't | 两组分段（✅/❌ 前缀） | 双列卡片 |

## Rule 10: 修改提纲后运行验证

修改提纲后，如果对应的 slide 已经生成：

```bash
python3 scripts/verify_slides.py --slide <N>
```

- 提纲改了措辞 → 同步更新 slides
- 提纲改了结构（表格→分段）→ 重新生成该页 slides

## Rule 11: 去 AI 味 — 像人说话，不像模型输出

提纲的文字最终会出现在 slides 和 speaker notes 中。AI 味重的表述会让听众觉得内容是凑的、不是想清楚的。

完整的反 AI 写作规范见 `personal-writing` skill（`.claude/skills/personal-writing/SKILL.md`），以下是提纲场景最常踩的坑：

**禁用词表：**

- "赋能"、"驱动"、"助力"、"使能" → 用具体动词：做了什么、改了什么、省了什么
- "不是X，而是Y" → 直接说 Y
- "不仅...更..." → 说一件事说清楚
- "深度融合"、"全面覆盖"、"高效协同" → 删掉或换成数据
- "总而言之"、"综上所述" → 删掉，直接说结论
- "想象一下..." → 直接陈述事实

**三条原则：**

1. **能用数字就不用形容词。** "$241 跑了 4 周" 比 "极低成本运行" 有力 100 倍。
2. **说人话。** 茶水间跟同事怎么说，提纲就怎么写。
3. **砍掉所有不提供新信息的词。** "通过XX实现了YY" → 直接说 YY。

## Anti-patterns

1. **把提纲当文章写** — 长段落、嵌套从句、数据嵌在句中。Slides 无法原样呈现。
2. **所有并列内容都用表格** — 并列概念用卡片更好，转换时必然产生文本差异。
3. **加粗标题带冒号** — 验证脚本匹配失败。
4. **正文和 speaker notes 混用** — 有信息价值的句子放在 `>` 中，导致内容丢失或多余。
5. **单元格塞长句** — 超过 40 字在 slides 中必然被截断或改写。
6. **AI 味表述** — "赋能体系"、"不是X而是Y"、"深度融合"。参见 Rule 11。
